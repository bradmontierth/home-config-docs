# Phase-two power migration proposal — 2026-09-27

**OFFLINE ONLY. No deployed flow edits, service calls, charger commands, helper changes,
restarts, or scheduled jobs.** Both Node-RED Admin API flow snapshots were re-read at
the end and had identical hashes. The reference model is not a deployable Node-RED
flow: it deliberately has no actuator/network adapters.

## What is built and what is proposed

`logic.cjs` implements pure reference logic for elapsed-time range/dryer/legacy
dishwasher detection, timestamped power validity/cache, time-weighted dishwasher
features, a dryer-outage dwell, acknowledgement-aware command suppression, coherent
EV power tuples, EV override handling, and a proposed stale-solar stop guard.
`logic.test.cjs` has 33 passing offline tests. `replay.cjs` replays today's recorded
raw samples through the reference classifiers. `migration-plan.json` names source
entities and the exact affected tabs. `source-fingerprints.json` identifies the
live policy functions inspected. No full flow snapshots or credentials are copied
into this proposal directory.

Production integration wiring, timer lifecycle, acknowledgements/readback,
contact/temperature handlers, and final rich-dishwasher state arbitration are not
implemented. They are specified below for review, rather than disguised as a
ready-to-import flow. Existing EV policy is inspected and retained conceptually;
the reference model tests its input/output safeguards, not every branch of the
large existing combiner.

## Source selection, time, and health

Use labeled Vue **Live** power for decisions, not the minute averages. The firmware
already corrects signs and doubles selected branches: do not multiply again in
Node-RED. Keep old IotaWatt entity/topic identities separate. There is no automatic
fallback to old main-Iota data: those CTs are removed. Keep IotaWattSolar's separate
outdoor heat-pump measurement, which has a different measurement boundary.

One ingress adapter normalizes `{circuit, watts, reportedAt, available, source}`.
Reject null, unavailable, NaN, negative consumption, future timestamps and older
reports. Do not use `Number(null)` or `Number('')`, which would invent zero load.
Availability is distinct from a known zero reading. HA state snapshots here contain
`last_reported`; `last_changed` cannot prove freshness when power is steady.

Subscribe only to the required power/availability and control entities. Use their
state events for immediate threshold decisions. Reconcile the selected sources
using a batch read every 10 seconds to get fresh `last_reported` values even if an
unchanged state produced no state-change event. Verify the installed HA nodes'
cache actually refreshes these reports; if not, use the batch API snapshot rather
than merely reading a stale Node-RED cache. Do not subscribe globally to all
`state_reported` events. The initial GET/get_states prototype used here confirms
fields exist, not that every upstream physical meter's reporting health is proven.

Proposed maximum source age is 20 seconds. Each report timestamp is normalized to
local monotonic time; never refresh it just because a poll succeeded. Use a single
local scheduler for due deadlines, or a single 1-second cheap deadline sweep across
armed timers; no 1-second traversal of entire appliance/HA service chains. When a
condition starts, arm its deadline. Opposite conditions cancel it. At expiry read
the **latest** cached state and health. Source gaps reset pending qualification;
no missing-data completion or accumulated timing across an outage. Keep confirmed
appliance status separate from a stale/unknown quality flag. Recovery needs new
valid qualification before further transitions.

High-frequency samples live in memory. Persist only low-rate checkpoints and state
transitions; do not write disk-backed flow/global context on every sample. On
Node-RED restart discard deadline timers/monotonic timestamps, fetch current HA
states and source health, and requalify. Reconcile durable completion helpers
without replaying prior notifications. Offline prototype classes start from explicit
initial state; production startup arbitration still needs wiring.

## Range / oven / toe-kick lighting

Existing tab `8123861fc119b96b`, switch `e150d598f34fd51f`, really uses **500 W**,
although its label says 50 W. Preserve that threshold for the first migration.
Vue source: `sensor.emporia_vue3_range_oven_power_live`.

- >=500 W: immediate Range true and indicator intent, once per transition.
- <500 W for 60 s: Range false.
- >100 W continuously for 180 s: OvenOn true, used by circulation-fan logic.
- <500 W for 300 s: OvenOn false.
- Keep the existing distinction between Range, OvenOn and RangeLights. Lighting
  remains active while either relevant active/heat latch requires it; preserve
  existing presets/brightness/manual ownership behavior at the actuator boundary.

Replace the growing `global.OvenStatus` timestamp array with one timestamp. Preserve
Away/Bedtime Range reminders, oven_status helper and Ecobee OvenOn consumers.
Only transitions reach existing WLED/HA action branches. Re-read actual actuator
state on reconnect before deciding whether an unchanged intent needs reconciliation.

**Gain:** a short stove activation is visible without waiting for the next nominal
10-second Iota poll and its last complete 5-second aggregate. Expected response is
roughly the 1-second averaging interval plus transport; this is not a measured
end-to-end latency guarantee. Today's replay catches the stove pulse at 10:13:59
and requests indicator off at 10:15:04. Existing timer semantics still suppress
relay/heater cycling. Constant-size state replaces an ever-growing array.

## Dishwasher: preserve useful semantics, fix time, reduce writers

Tab `ee0f1588760b9b3b`, source link-in `b470598e126b7d11`. Use
`sensor.emporia_vue3_dishwasher_power_live` instead of legacy "Kitchen".
Input 10's pre-16:05 readings were UPS load and are excluded from dishwasher replay.

Initial authoritative path preserves legacy thresholds/deadband:
>40 W arms 30 s running qualification, <10 W cancels it; 10..40 W holds the existing
qualification. <10 W arms 180 s completion, >40 W cancels it. Require 10 minutes of
observed running-state duration before clean, otherwise preserve dirty/short-run
handling. Timer time is never credited across a freshness gap. Preserve contact,
temperature, unload/dirty and notification-enable logic as explicit inputs. Door
changes must update the classifier's selected state as well as the HA helper;
otherwise a retained private running state could overwrite a user's dirty state.

The newer `theMagic` classifier (`29bbcc343e24ac09`) currently assumes 5 s per sample
although normal source cadence is about 10 s. Its "4-minute" 48-sample window is
about 8 minutes today and only 48 seconds if naively fed 1 Hz. Proposed replacement:
4 real minutes, 120 real minutes since recent high, 30 real seconds fast-running,
10 real minutes since last high before drying, 2 real minutes of clean release,
90 real seconds clean-tail evidence and 4 real minutes other-transition smoothing.
Use time-weighted windows, full-enough coverage, and bounded buffers; timestamps
replace counts. Evaluate richer features every 5 s; retain peak/min/mean information
in each bucket rather than point-sampling and losing heater pulses.

Reference `DishwasherFeatures` implements the bounded time-weighted features and
fast-running gate; sticky drying/terminal-clean arbitration remains a specified
shadow classifier, not a promoted second control writer. Keep `dishwasher_new`
read-only/shadow initially, or mirror the selected state without granting it
notification authority. Preserve `notify_on_dry`, but only a qualified transition
from the selected classifier may consume it or notify. The rich classifier's new
wall-time settings intentionally correct existing cadence errors and need full-cycle
validation before live promotion.

**Gain:** no 1-Hz-induced premature state changes, no duplicate status write on every
sample, and clearer circuit attribution. Today's post-relocation replay qualifies
running at 16:06:33. It does not prove complete clean/drying behavior because the
captured cycle, door/temperature inputs and end state are not fully annotated.

## EV: coherent inputs, unchanged policy, controlled commands

Tab `7fa25727b15db1f0`; preserve policy in `b0b4f535c19d2ed7` while replacing its
input assembly and output dispatch to `d8423915df88b573`. Retain 6–32 A limits,
18:00–22:05 TOU block, ASAP/recovery/tonight/solar priority, 30% low-SOC recovery
floor and 38% recovery target, 91%/89% Powerwall hysteresis, 120 s solar qualification,
20-minute solar minimum run, and reserve-reset timing. Keep Powerwall reserve
commands on their own acknowledgement-aware gate; currently a proposed command
can be latched as sent before success, which must be corrected in production wiring.

`automation_disable` **yields control**; it does not mean stop. A known grid outage
still overrides it and requests stop. Clear pending normal intents when manual
takeover happens. Do not convert unavailable grid state to false. TOU remains a
policy hard stop; schedule its boundary explicitly so it does not wait for a
changed power value. Recheck all overrides immediately before dispatch.

Required load expression after boundary validation:

`home = Vue mains A + Vue mains B + separate IotaWattSolar outdoor heat-pump watts`

`available solar = Powerwall solar - (home - Vue EV watts)`

Never sum the 16 branches as a replacement for mains. Never subtract EV twice.
The current old total-home helper still references the old source; freshness alone
cannot make removed CT measurements valid. Indoor mains references/signs and outdoor
coverage must pass a cross-check before enabling this self-balancing source change.
The draft uses source age <20 s and maximum power timestamp skew 5 s, applied to
matched measurement windows, not just unrelated latest values. These are proposed
limits; observed source cadence/skew must qualify before activation. Powerwall/EV
SOC and override freshness policies are separate from high-rate wattage (e.g. battery
SOC can legitimately update more slowly). Never require SOC to update every second.

Cache incoming 1 Hz EV/mains data. Evaluate normal policy every **5 s**, regardless
of which input changed. Emit a normal charger command only for a changed target,
with at least **10 s between attempts** and integer-amp targets. Deduplicate only
after successful acknowledgement; validate readback for actuation. Retain newest
desired target, not a FIFO. Failures allow bounded retries and a health diagnostic.
Known outage stops bypass ordinary cooldown. The dispatcher must reconcile an
in-flight old normal request that finishes after a stop; the offline gate rejects
its late acknowledgement but cannot by itself prevent hardware request reordering.

No arbitrary periodic keepalive is assumed. Read-only GET /status and GET /override
succeeded; current override exposed `auto_release: true`. That is not evidence of
an expiring lease. Installed firmware's auto-release/reconnect semantics still need
verification. Read back at a low rate (proposed 30 s) and on reconnect; resend only
when the intended state is not in effect. Keepalive stays disabled until a real
requirement is found. The charger's returned clock was not synchronized, so don't
use that timestamp as the source of truth for freshness.

Proposed, explicitly new stale-data behavior: no increase or new solar start from
invalid inputs; hold an automation-owned solar session at its last acknowledged
setting for at most 30 s after invalidity detection, then request stop even if the
20-minute minimum run has not expired. Requalify the 120-second start condition
when coherent inputs return. This guard does not take over an automation-disabled
or explicit manual/ASAP/overnight/recovery session; those retain their own valid-input
and outage requirements. A known outage always stops promptly. This policy needs
review because it intentionally strengthens the existing unbounded stale-cache behavior.

**Gain:** react to real load changes without one HTTP request per power report.
5-second evaluation is 720 evaluations/hour versus 3,600 at naive 1 Hz; the normal
10-second command bound is at most 360 attempts/hour, usually far fewer because
unchanged targets produce none. Synthetic stable-target test produced one command
rather than 3,600 attempts after acknowledgement. These are model results/caps,
not measured savings against today's running charger traffic.

Inventory and move `global.Tesla`, `global.AC`, `global.Furnace`,
`global.dishwasherPower`, Range/OvenOn and the Tesla-not-charging alert's solarExcess

Audit both writers and readers when assigning new source ownership.

Keep existing Energy MQTT Sensors tab `afea81d223c193eb` at 15 s. Replace its
validated total-home source when ready; do not turn SQL and discovery into a 1 Hz
pipeline. Publish MQTT discovery at startup/configuration change, not per sample.
Do not publish Vue under old IotaWatt identities without an explicit, documented
historical boundary. Point dashboard live-breakdown entities to new labels; labels
for shared circuits must remain honest (Washer/Bidet, Loft/Bath/Fan etc.).

HA already excludes the fast Vue streams. Preserve those exclusions. History uses
minute-average power. The 16 legacy HA power-integration helpers and downstream
utility meters need a **separate energy migration**: retargeting them directly to
1 Hz power could recreate recorder churn through derived kWh entities. Firmware
currently exposes only the existing fridge daily-energy counter, which resets on
reboot. It is not a persistent replacement for all historical counters. Design
persistent device-integrated totals with 60 s publishing (or a separately validated
bounded integrator) and an explicit cutover baseline before energy/dashboard history
migration. No silent energy reset or retroactive rescaling. Preserve legacy SQL
archives and the seven-day EV Auto Tonight analysis; assess whether new-source
history is sufficient before making its old data query authoritative again.

## Deployment proposal, later only

1. Finish Node-RED adapters and HA-service/readback wiring from fresh GET /flow
   snapshots, review per-tab diffs, and compare source fingerprints for drift.
2. Deploy **shadow only**: candidate transitions and desired commands go to bounded
   logs; no helpers/globals consumed by live automations, no device commands. Observe
   at least a complete dishwasher and dryer cycle plus outages/reconnect simulations.
   Offline replay has no unambiguous ground-truth trace for every stage.
3. Switch one consumer at a time: range, dryer/outage, legacy dishwasher, compatibility
   globals/dashboard; EV only after mains/outdoor/lease and policy tests pass.
4. Disable/detach the corresponding old writer before enabling the new one. Both
   ends of any new Node-RED link must be updated. Use GET/PUT /flow/TAB_ID, not
   deployed files or broad subflow changes. Per-tab deploy restarts its nodes:
   initialize from live state, wait for HA readiness and avoid startup notifications.
5. Verify an acknowledgement/readback for each action class; no repeated stable-state
   commands, no false completion on loss, no stale normal command after an urgent stop.
   Record why each source/command was accepted or blocked at transitions only.
6. Rollback means disable the new actuator writer and restore reviewed tab snapshots;
   **do not automatically reactivate removed-CT IotaWatt actuation**. Leave consumers
   in manual/held mode until a usable source is selected. Energy helper migration is
   its own reviewed step and any HA restart still needs prior approval.

## Evidence and limits

33 offline tests passed: cadence invariance, short pulses, fresh unchanged reports,
invalid/future/out-of-order data, dropout gaps, bounded windows, duplicate commands,
retry/urgent precedence, manual-control semantics, coherent EV subtraction and the
proposed stale-solar rule. Tests run with `node --test emporia-vue3/phase2/logic.test.cjs`.

25,850 recorded 1-second snapshots, 10:06:45–17:18:07 MDT, were replayed. Selected
results: range indicator on 10:13:59/off 10:15:04; dishwasher running 16:06:33;
actual sustained dryer running 16:17:08. These are **would-have** transitions of the
reference model. Notifications, HA outputs and actual charger response are not
validated by this replay. The replay excludes input 10's former UPS history.

Live flows on both ports 1880 and 1881 were byte-content equivalent under canonical
JSON hashing before/after the work (`no-deploy-verification.json`). Only local
proposal/test files were written. No external notifications were sent.

References:
- [Node-RED rate limiting with dropped intermediate messages](https://cookbook.nodered.org/basic/rate-limit-message-stream)
- [HA last_reported and state_reported semantics](https://developers.home-assistant.io/blog/2024/03/20/state_reported_timestamp/)

A Delay node with dropped intermediate messages is suitable for low-priority display
or diagnostics. For control, cached newest state plus a scheduled re-evaluation is
more explicit: it cannot retain a stale command while overrides change, and it does
not delay the outage path. Recorder exclusion is independent of event delivery.
