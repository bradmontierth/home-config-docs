## Finding 1: the automations ARE machine-exportable

Maker API does not expose apps, but the hub's own UI endpoints do, and with hub
security off they need no login. Verified against his hub:

```text
GET /hub2/appsList                  JSON tree of every installed app, parent -> child, ids, paused/disabled
GET /installedapp/statusJson/<id>   JSON of one app: appSettings, appState, eventSubscriptions, scheduledJobs
GET /installedapp/configure/json/<id>   JSON of the config page (rendered text of the rule)
GET /hub2/devicesList               JSON of all devices (id, label, room)
GET /device/fullJson/<id>           one device in full
```

Example, app 62 "Living Room: button 1 doubleTapped" decodes straight from
`appSettings`:

```text
tDev1 = [30]  ButtontDev1 = 1  tstate1 = doubleTapped      -> trigger: device 30 "Living Room" (Zooz Central Scene Switch), button 1, double tap
actType.1 = switchActs  actSubType.1 = getOnOffSwitch  onOff.1 = true
onOffSwitch.1 = [23,24,25,26,27,28]                        -> action: turn ON devices 23-28
```

So no copy/paste from screens. A ~100-line script crawls the tree and writes the
whole inventory. These endpoints are undocumented, so treat the dump as a
one-time snapshot (re-runnable), not an API to build on.

Also found: app 297 "Export/Import/Clone" is installed. It is a hub-to-hub
restore format, not needed given the above.

From the research pass (docs / forum / source, not all tested on his hub):

- `statusJson` and `device/fullJson` need firmware 2.4.0+; he is on 2.4.4, fine.
- `configure/json/<id>` carries the rendered rule text as HTML paragraphs
  ("Dim: X to 30"); strip the spans and use it as the human-readable line in
  the inventory, with `statusJson` settings as the machine-readable truth.
- `GET /installedapp/disable?id=<ID>&disable=true|false` is the scriptable
  version of the Apps-list Disable checkbox. Untested here; it is a write, so
  try it first on one PoC rule. Disable = platform-level, no app code runs,
  name shows struck through. Pause = per-app, rule stays viewable. Either is
  reversible; Disable is the one an agent can do itself during a cutover.
- The `hubitat device` node forwards EVERY event with no change filter, so a
  repeated `pushed = 1` fires every time (what we want for buttons).
- Zooz built-in drivers emit `pushed / held / released / doubleTapped` with the
  button number as the value. Triple-tap and up needs the community driver.
- hacs-hubitat takes over the POST URL of the Maker API instance it uses. He
  already has separate instances (184 Node-RED, 236 HA); keep it that way.
- Hub backups (`.lzf`, encrypted H2) are not a practical route. Skip.
- Room Lighting / Motion Lighting have no rendered text, but he has none
  configured, so that gap does not apply.

## Finding 2: convert using Hubitat device ids, not HA entities

The exported rules reference Hubitat device ids, and `node-red-contrib-hubitat`
nodes take those same ids. Converting through Hubitat nodes is a 1:1 mapping
with nothing to cross-reference, and the path is one hop shorter
(hub -> webhook -> Node-RED -> Maker API -> hub) than going through HA.

HA stays what it is good at: the room-organised dashboard and the friendly
names. Add the HA palette to Node-RED later only when an automation needs a
non-Hubitat thing (Frigate person, Emporia, Airthings).

Trade-off to say out loud: button automations then depend on the N100 being up.
Single-tap still works with the N100 down because that is the switch's own
relay; double-tap / held scenes would not. His current uptime is 11 weeks.
Mitigation is keeping the Hubitat rules PAUSED rather than deleted, so
fallback is un-pausing.
